# Caddy sites and preview entry

An operator-selected fixed read capability runs Caddy's own adapter. The platform parses the real JSON and registers sites without changing website directories, theme sources or existing Caddy rules. Newly discovered sites belong to the synchronizing administrator; other accounts use explicit site memberships. Manager/control hostnames are excluded.

Inventory classifies static, redirect, proxy and other configuration, retaining hosts, listeners, recognizable document roots and redirect targets. Composite configurations are never reduced to a lossy template. Missing source routes are marked absent rather than deleting authorization/history. Imported private/ready values are registration metadata, not network reachability or health claims.

The platform home separates platform-managed sites from Caddy inventory. Only static websites with an actual document directory can be converted, after an operator registers their full source and immutable template. Redirects, proxies and unsupported entries stay in Caddy configuration management. Conversion records the current settings without changing live configuration, website contents or release pointers; it does not select a theme.

For registered sources, the configuration page separates saving a draft, validating the exact revision, deploying it and restoring a previously applied revision. Strong ETags prevent stale edits; source digests detect operator changes. Compression, cache policy and baseline response headers are finite settings, individually enabled by the operator. Preserve keeps the complete original rule set, including shared snippets. Arbitrary Caddyfile text, filesystem paths, upstreams and commands are never accepted from HTTP. A failed apply restores the last good source and reports failure. Root-owned plans and original revisions are kept outside the application account's reach; HTTP returns only safe settings and revision metadata.

Website source kind and workspace capabilities are separate. Adopted static websites can select platform content and registered themes; selecting a theme enables its configuration, builds and isolated previews. Redirects and proxies retain their Caddy surfaces. Backend guards use the same capability boundary as navigation. A Caddy file_server alone does not identify a registered theme. See [content and publishing workflows](./CONTENT_WORKSPACES.md).

The manager runs as an ordinary user. Only root-owned, argument-free helpers are granted; source control uses a separately installed root-owned binary with bounded JSON on stdin. Caddy validates and reloads as caddy, without a general root shell. The Caddy admin API uses a filesystem-protected Unix socket. Mutations require a full administrator session, site ownership and CSRF, rechecked in the database transaction. Raw configuration and certificates are not exposed over HTTP. `FUYAO_ADMIN_CADDY_MANAGEMENT_ENABLED` independently enables source deployment for registered sites; the theme publishing switch can remain off.

Install the inventory sanitizer alongside the source controller: the snapshot helper emits a versioned safe inventory, not Caddy's complete JSON. In source-control deployments, revoke the old arbitrary-snippet write permission and generic apply sudo grant. Master files, source templates and controller binaries remain root-owned. Applying a revision checks the running Unix-socket configuration before and after reload; an unchanged source digest alone is insufficient because a preserve-only apply can create a new root revision. Database/root-revision disagreement blocks further changes for operator reconciliation.

Preview URLs use `https://preview.manager.fuyaoskyrocket.ing/formal-host/original-path?lease=short-capability`, falling back to the site slug when no formal hostname exists. This separate HTTPS host receives no manager-session cookie. A controlled wrapper embeds unchanged artifacts on a separate HTTPS port, preserving production routing semantics. JavaScript is not rewritten and publishing base paths are not changed. An operator-configured port offset separates TLS listeners from site publication ports.

Closing cancels pending issuance, revokes grants, stops backend listeners and releases allocations. Reload only reauthorizes the same active incarnation; closed wrappers return 410 and cannot recreate it. Caddy maps closed upstreams to non-cacheable 410. Preview access logging is skipped and default logs filter request URIs and headers so capabilities are not retained.

HTTPS session/auth-transaction cookies use `__Host-`, Secure, HttpOnly, Path=/ and no Domain. Legacy names and duplicate authentication cookies are rejected. Existing users sign in again after upgrade; account and passkey records remain intact. HTTP localhost development stays compatible.

The API page reads authenticated `GET /api/v1/openapi`, backed by `contracts/openapi/openapi.yaml`. It displays only declared version/authorization metadata.

## Source-controller installation

Build `./cmd/fuyao-caddy-control` and `./cmd/fuyao-caddy-inventory` from `backend/` for the server architecture. Install both binaries as root-owned files under `/usr/local/libexec/`, and the matching wrapper scripts from `deploy/fuyao-admin/` under `/usr/local/sbin/`. The application must not be able to replace any ancestor directory. Grant sudo only for the zero-argument `fuyao-caddy-control` and `fuyao-caddy-snapshot` wrappers; remove the legacy generic apply grant and application write ACLs on imported Caddy fragments. Validate sudoers with `visudo -cf` before installation.

Each eligible site has one root-owned registration at `/etc/fuyao-caddy-control/sites/<sourceKey>.json`. Use the inventory's exact source key, not a domain-derived guess. The record contains `siteKey`, `kind: static`, `staticRoot`, `masterFile`, `sourceFile`, `baseTemplate`, `masterTemplate`, `initialDigest`, `capabilities` and `preserve`. All paths are operator-controlled. `staticRoot` must exist; source/template/master files must have trusted owners and unwritable parent directories.

Extract the complete existing host block without simplifying it. Replace that block in the master with an absolute import of its protected source file. Keep shared snippets and other hosts intact. The immutable base template substitutes only the enabled `__FUYAO_COMPRESSION__`, `__FUYAO_CACHE_CONTROL__` and `__FUYAO_SECURITY_HEADERS__` slots. `preserve` stores their exact original fragments; rendering all three preserve values must equal the original source byte for byte. The master template substitutes exactly one `__FUYAO_SITE_SOURCE__` marker. Before changing live configuration, compare complete adapted configurations; approve only the additional automatic hide paths of protected configuration files and reject every other difference.

Caddy needs read/traverse access to live source and validation-work files; it does not need write access. Keep registration/templates and `/var/lib/fuyao-caddy-control/` inaccessible to the application. The controller uses the fixed `/run/caddy/admin.sock` endpoint and the daemon's environment to avoid losing parse-time secrets. Enable the independent source-control setting only after these checks. Changing the master template or other imported configuration invalidates existing validation plans and may require operator reconciliation.

The sudo helper inherits the application's filesystem namespace. With `ProtectSystem=full`, allow only the root-owned source directory through `ReadWritePaths`; Unix ownership must still deny writes by the application user. Keep templates and executables read-only. A successful root-shell operation does not verify the service namespace: exercise deployment through the real authenticated management API.
