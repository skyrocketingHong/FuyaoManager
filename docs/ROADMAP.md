# Management Platform Roadmap (MVP Iteration Ledger)

English | [简体中文](./ROADMAP_ZH.md)

Agile ledger for the content management platform. Each work package lands a running, verified increment; nothing is listed as done before it is implemented and verified. On 2026-11-11 the "Next" section was restructured around the approved theming and React migration track (T1 to T5); the feature packages that follow keep their original scope.

## Done

1. **Backend MVP (local development)** (`admin/backend`): PostgreSQL + SQL migrations, passkey-only WebAuthn auth (discoverable credentials, UV required), CLI (`migrate`, `serve`, `bootstrap-admin`, `create-site`), cookie sessions with CSRF/Origin enforcement, site list/detail/settings with transactional ETag concurrency. Loopback-only. Contract: `contracts/openapi/management.yaml`.
2. **Hardening pass**: transactional first-enrollment closure (advisory lock; concurrent completions admit exactly one), permit expiry re-checked at verify time, full-ETag If-Match binding (wildcard rejected), stable per-session CSRF token (multi-tab safe), request limits and single-object JSON on verify paths, loud TTL validation, CORS ETag exposure.
3. **Admin frontend MVP** (`admin/frontend`): enrollment, login/logout, site list/detail/settings with dirty-field patches, 412 conflict recovery, and viewer read-only; generated API types with drift check; zh-CN/en-US with Crossfade; day/night themes; same-origin dev proxy topology (port 5174 pinned, loopback only). The non-browser protocol integration (backend serve + dev proxy + cookie/origin flows) is exercised by this package's verification; real platform-authenticator ceremonies and visual acceptance remain with the user.
4. **T1 — Theme contract v1** (`contracts/theme/`): machine-checkable contracts for the theme manifest (`theme.json`), the build-input snapshot metadata (`input.json`), and the release metadata (`release.json`), all JSON Schema draft 2020-12, with public-safe positive and negative fixtures covering version, path-traversal, capability, URL-convention, digest, and unknown-field rejections. Consumable validation landed with the contract: Go package `admin/backend/internal/themecontract` (schema compilation, theme-config cross-validation, manifest/input pairing, capability and URL-convention gap helpers) and the `fuyao-admin validate-theme` CLI. Reserved identifiers: first theme `fuyao-homepage`, first trusted adapter `node22-sveltekit-static`. Contract docs: `contracts/theme/README.md`. Verified by `go test ./internal/themecontract/ ./internal/cli/`, `go vet`, `gofmt`, `go build`, prettier, and the repository privacy audit.
5. **T2 — First theme registration** (`site/` as `fuyao-homepage`): `site/theme.json` and `site/theme.config.schema.json` mirror the contract fixtures; `prepare-build-inputs.js` writes `private/input.json` (theme id/version bound to `version.json`, mismatch aborts the build) with the three input digests — public content tree plus the content path/media mapping, site config, theme config — and the `public-config.json` to `site-config.json` rename covers every real consumer (`vite.config.ts`, the build context, `generate-blog-index.js`, `prepare-content-release.js`). `--frozen=<snapshot>` (or `FUYAO_FROZEN_INPUT`) gives T3 a minimal consumption entry: the frozen snapshot is verified read-only (identity, protocol, and digest conflicts are rejected) and only its writable build-asset mirror feeds SvelteKit. Shared logic lives in `site/scripts/lib/theme-input.js`. Verified by `fuyao-admin validate-theme` on `site/`, svelte-check, the 99-test site suite (including four new theme-input tests), lint, a full build, and a normalized artifact diff against a pre-change baseline: 250/250 files, all 99 non-hashed paths identical, remaining differences are `__BUILD_TIME__`/`__sveltekit_` derived asset-hash renames and build-time fields only.
6. **T3-a — Backend theme registry and per-site selection** (`admin/backend`): migration 0003 adds the `themes` catalog and `site_theme_selections`; the operator-driven `fuyao-admin register-theme` CLI (the only registration entry — the HTTP API never accepts paths, commands, or Git addresses) validates a theme root against `contracts/theme`, enforces the trusted-adapter list, resolves the source to the absolute realpath of the validated root, and stores manifest + SHA-256 digest + config schema; re-registration is idempotent only when the full identity (digest and schema, declared/omitted included) matches. HTTP surface: `GET /api/v1/themes` and `GET/PUT /api/v1/sites/{siteId}/theme` under the existing membership/CSRF/Origin/If-Match model with an independent revision counter (`-t` tags, `t0` = unselected); `themeConfig` omission defaults to `{}` while explicit `null` is rejected; invalid configs get a path-free 422; without `FUYAO_ADMIN_THEME_CONTRACTS` the save fails 503 instead of skipping validation. OpenAPI updated with generated types and drift/lint green. Verified against the task PostgreSQL 18 instance: full `go test ./...` plus gofmt/vet/build, catalog-read/persistence/permission/stale-ETag/concurrent-first-save cases, and registration-conflict regressions; evidence under `.fuyao/theme-migration/verification/t3a/`.

7. **T3-b1 — Real snapshot builds and private preview loop** (`admin/backend` + `site/`): migration 0004 persists per-site build tasks whose creation transaction freezes the exact version view (site settings snapshot + revision, theme selection revision, theme identity and config); the executor role is a cluster-wide advisory lock — only its holder recovers interrupted `running` rows as failed and re-enqueues `queued` ones, and it holds the role until its worker drains, so a second instance never kills the first one's active builds. The runner binds every stage to the registered theme root, re-verifies the on-disk `theme.json` and config schema digests against the registered identity (catching post-registration edits), checks the trusted server-side site requirements against the theme's capabilities/URL conventions before building (explicit missing-item failures), runs the theme's own Node preparation with the database-saved settings (`site.name/description/defaultLocale`, description also feeds public SEO metadata via `site.site.description`) and theme configuration injected as JSON files, then seals snapshot and artifacts by **copy + verify + freeze** into per-task directories — the shared theme workspace (`build-inputs/current`, `build/`, `build-context.json`) is restored/kept intact. Commands run with a scrubbed environment and their own process group (group-kill on cancel), never inheriting database URLs or admin secrets; this is environment and process hygiene, not an OS sandbox. Preview: each succeeded build gets its own loopback-only origin (per-build listener) behind a one-time entry token exchanged for an HttpOnly cookie — root-absolute assets, deep routes, and the declared SPA fallback all behave as in production, builds/sites never cross-serve, and the origin is distinct from the management API so theme scripts cannot read management responses. HTTP surface: `POST/GET /api/v1/sites/{siteId}/builds`, `GET .../builds/{buildId}`, `POST .../builds/{buildId}/preview-links` under the existing membership/CSRF/Origin model; OpenAPI and generated types updated in the same change. Verified against the task PostgreSQL instance: the closed-loop test drives two real API-created builds with real Node/SvelteKit builds through the preview HTTP surface (DB settings frozen into the snapshot, digests recorded, artifacts read-only, second build's origin serving its own content, cross-origin tokens and anonymous access rejected) plus a capability-gap build persisted as an explicit failure; full backend suite, affected site config/theme-input tests, OpenAPI drift check, and prettier green. Evidence under `.fuyao/theme-migration/verification/t3b1/`.

## Next (in order, one package at a time)

7. **Real-browser regression** with actual platform authenticators (Touch ID / hardware keys) and visual acceptance, driven by the user.
8. **T3 — Backend publish pipeline** — guarded build executor, preview, verification, atomic switch, rollback (registry and per-site selection landed as T3-a; snapshot builds and private preview landed as T3-b1 above — this remaining scope is publication: release verification against `release.schema.json` and `requiredArtifacts`, atomic switch, rollback, release records).
   - Boundary: `admin/backend` gains snapshot preparation from platform content consuming the T3-a selection records and trusted manifest data, a build executor restricted to the enumerated adapter (no management keys, no database access, no arbitrary commands), private preview roots, publication verification against `release.schema.json` and each manifest's `requiredArtifacts` plus the capabilities/URL-convention gap check that blocks publication, and release records carrying the content, theme, and configuration versions plus task state and failure records; OpenAPI updated in the same change for every new HTTP endpoint.
   - Done when: an end-to-end local publish driven from the admin API over existing site content produces a release equivalent to the T2 direct build; a failing or incompatible build leaves the previous release active and reports the exact missing capability or URL-convention items; rollback restores an earlier exact triple per site.
   - Verify: backend integration tests against the task PostgreSQL instance; OpenAPI drift and semantic lint; publish, incompatibility, failure, and rollback evidence logs under `.fuyao/theme-migration/verification/`.
9. **T4 — Admin frontend migration to React + TypeScript + Vite + official Ant Design**.
   - Boundary: rebuild the six routes, passkey enrollment and login, session handling, site list/detail/settings, CSRF handling, ETag/412 conflict recovery, cross-site request isolation, zh-CN/en-US switching, light/dark themes, and reduced-motion support on React with native antd components and design tokens, using Simple Icons for brand icons (accessible names preserved, no decorative filler); the management stack is TypeScript + React + Ant Design + Simple Icons on the frontend only — the Go backend stays Go (no server-side TypeScript migration), and the public site stays Svelte as the first theme. Keep the OpenAPI contract, the framework-agnostic pure-TS API clients (`client.ts`, `management.ts`, `passkey.ts`, generated `schema.d.ts`), and the Vite same-origin proxy topology (port 5174 pinned, WebAuthn origin unchanged).
   - Done when: per-route feature parity with the Svelte console is demonstrated (no functional regression); type generation drift check, semantic OpenAPI lint, typecheck, tests, and build pass; no Svelte runtime remains in `admin/frontend`.
   - Verify: ported and extended vitest suites; root `npm run admin:check && npm run admin:test && npm run admin:build`.
10. **T5 — Joint debugging and local preview delivery**.
    - Boundary: run the Go management service, the React admin console, the local PostgreSQL instance, and the first-theme site or private preview together; hand the user the URLs and stop instructions; keep logs, credentials, and private data out of Git.
    - Done when: the user can complete the full local flow (login, configure, publish, preview, rollback); visual acceptance and real platform-authenticator ceremonies remain with the user by design.
11. **Articles**: list, edit, publish; markdown pipeline reuse from `site/` scripts.
12. **Pages and layout modules**; site-scoped content boundaries.
13. **Multi-site fan-out** and membership management UI.
14. **Server-side secret configuration and GitHub source updates**: build, deploy, and rollback entries land with T3; this package completes the remaining operations surface with task state and failure records.
15. **Migrate remaining `site/scripts` responsibilities** (media processing, validation, watchers, external data cache, versioning, migration, release) into the backend; retire old entry points only after parity acceptance.
16. **Tailscale private-network exposure** and the 30-minute public gate; production deployment path.

Not planned for MVP: importing production data, migrating real keys, pulling production deployments.
