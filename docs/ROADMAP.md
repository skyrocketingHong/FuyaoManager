## Review 2026-11-12 (Codex acceptance, changes required)

The N1-N5 delivery claims below were audited against independent probes
(`.fuyao/cms-n/verification/codex-review-20261112/`). The earlier "all
verified, no outstanding items" statements were overclaims: concurrent
content saves lost updates, the edge could regress under delayed publish
callbacks, private sites still bound wildcard listeners, album ordering and
managed fields did not survive the loop, previews leaked capacity on expiry,
and the React editors discarded in-flight drafts. Repairs R1-R8 (commits
from `fix(edge,content)...` onward) land the corrections with regressions;
the entries below are kept as the original delivery record and are
superseded where they conflict with this section.

1. **Backend MVP (local development)** (`admin/backend`): PostgreSQL + SQL migrations, passkey-only WebAuthn auth (discoverable credentials, UV required), CLI (`migrate`, `serve`, `bootstrap-admin`, `create-site`), cookie sessions with CSRF/Origin enforcement, site list/detail/settings with transactional ETag concurrency. Loopback-only. Contract: `contracts/openapi/management.yaml`.
2. **Hardening pass**: transactional first-enrollment closure (advisory lock; concurrent completions admit exactly one), permit expiry re-checked at verify time, full-ETag If-Match binding (wildcard rejected), stable per-session CSRF token (multi-tab safe), request limits and single-object JSON on verify paths, loud TTL validation, CORS ETag exposure.
3. **Admin frontend MVP** (`admin/frontend`): enrollment, login/logout, site list/detail/settings with dirty-field patches, 412 conflict recovery, and viewer read-only; generated API types with drift check; zh-CN/en-US with Crossfade; day/night themes; same-origin dev proxy topology (port 5174 pinned, loopback only). The non-browser protocol integration (backend serve + dev proxy + cookie/origin flows) is exercised by this package's verification; real platform-authenticator ceremonies and visual acceptance remain with the user.
4. **T1 — Theme contract v1** (`contracts/theme/`): machine-checkable contracts for the theme manifest (`theme.json`), the build-input snapshot metadata (`input.json`), and the release metadata (`release.json`), all JSON Schema draft 2020-12, with public-safe positive and negative fixtures covering version, path-traversal, capability, URL-convention, digest, and unknown-field rejections. Consumable validation landed with the contract: Go package `admin/backend/internal/themecontract` (schema compilation, theme-config cross-validation, manifest/input pairing, capability and URL-convention gap helpers) and the `fuyao-admin validate-theme` CLI. Reserved identifiers: first theme `fuyao-homepage`, first trusted adapter `node22-sveltekit-static`. Contract docs: `contracts/theme/README.md`. Verified by `go test ./internal/themecontract/ ./internal/cli/`, `go vet`, `gofmt`, `go build`, prettier, and the repository privacy audit.

Shared logic lives in `site/scripts/lib/theme-input.js`. Verified by `fuyao-admin validate-theme` on `site/`, svelte-check, the 99-test site suite (including four new theme-input tests), lint, a full build, and a normalized artifact diff against a pre-change baseline: 250/250 files, all 99 non-hashed paths identical, remaining differences are `__BUILD_TIME__`/`__sveltekit_` derived asset-hash renames and build-time fields only.
6. **T3-a — Backend theme registry and per-site selection** (`admin/backend`): migration 0003 adds the `themes` catalog and `site_theme_selections`; the operator-driven `fuyao-admin register-theme` CLI (the only registration entry — the HTTP API never accepts paths, commands, or Git addresses) validates a theme root against `contracts/theme`, enforces the trusted-adapter list, resolves the source to the absolute realpath of the validated root, and stores manifest + SHA-256 digest + config schema; re-registration is idempotent only when the full identity (digest and schema, declared/omitted included) matches. HTTP surface: `GET /api/v1/themes` and `GET/PUT /api/v1/sites/{siteId}/theme` under the existing membership/CSRF/Origin/If-Match model with an independent revision counter (`-t` tags, `t0` = unselected); `themeConfig` omission defaults to `{}` while explicit `null` is rejected; invalid configs get a path-free 422; without `FUYAO_ADMIN_THEME_CONTRACTS` the save fails 503 instead of skipping validation. OpenAPI updated with generated types and drift/lint green. 7. **T3-b1 — Real snapshot builds and private preview loop** (`admin/backend` + `site/`): migration 0004 persists per-site build tasks whose creation transaction freezes the exact version view (site settings snapshot + revision, theme selection revision, theme identity and config); the executor role is a cluster-wide advisory lock — only its holder recovers interrupted `running` rows as failed and re-enqueues `queued` ones, and it holds the role until its worker drains, so a second instance never kills the first one's active builds. The runner binds every stage to the registered theme root, re-verifies the on-disk `theme.json` and config schema digests against the registered identity (catching post-registration edits), checks the trusted server-side site requirements against the theme's capabilities/URL conventions before building (explicit missing-item failures), runs the theme's own Node preparation with the database-saved settings (`site.name/description/defaultLocale`, description also feeds public SEO metadata via `site.site.description`) and theme configuration injected as JSON files, then seals snapshot and artifacts by **copy + verify + freeze** into per-task directories. Since the workspace-isolation rework, every writing step runs inside the task's private copy of the registered theme root (`taskDir/theme`, excluding node_modules and mutable build state, dependencies resolved from the repository tree, contract schemas injected via `FUYAO_THEME_CONTRACTS`), so the registered source — including its `.fuyao` state and `build/` — is never written, moved, or restored; each task records a full per-file source manifest (aggregate digest plus file count, migration 0005) that is broader than the theme.json digest. Commands run with a scrubbed environment and their own process group (group-kill on cancel), never inheriting database URLs or admin secrets; this is environment and process hygiene, not an OS sandbox. Preview: each succeeded build gets its own loopback-only origin (per-build listener) behind a one-time entry token exchanged for an HttpOnly cookie — root-absolute assets, deep routes, and the declared SPA fallback all behave as in production, builds/sites never cross-serve, and the origin is distinct from the management API so theme scripts cannot read management responses. HTTP surface: `POST/GET /api/v1/sites/{siteId}/builds`, `GET .../builds/{buildId}`, `POST .../builds/{buildId}/preview-links` under the existing membership/CSRF/Origin model; OpenAPI and generated types updated in the same change. Verified against the task PostgreSQL instance: the closed-loop test drives two real API-created builds with real Node/SvelteKit builds through the preview HTTP surface (DB settings frozen into the snapshot, digests recorded, artifacts read-only, second build's origin serving its own content, cross-origin tokens and anonymous access rejected) plus a capability-gap build persisted as an explicit failure; full backend suite, affected site config/theme-input tests, OpenAPI drift check, and prettier green. Evidence under `.fuyao/theme-migration/verification/t3b1/`.

8. **T3-b2 — Publish and rollback closed loop** (`admin/backend`): migration 0006 adds `site_releases` (frozen theme identity, the three input digests, routes, reasons, live/superseded/failed status, persisted failure records) and the `sites.current_release_id` pointer; migration 0007 narrows uniqueness to active releases only (live/superseded) — failed attempts stay in history, the same build can be retried, and republishing a released build answers 409. The `internal/publish` manager re-checks the trusted site requirements (missing capabilities/URL conventions recorded precisely), verifies the manifest's `requiredArtifacts`, generates and contract-validates `release.json` against `release.schema.json`, seals the artifacts by copy + verify + freeze into `ReleasesRoot/<site>/<buildID>`, and switches the live release atomically inside one transaction holding the per-site publish advisory lock (base state read under the lock). Any stage failure persists a failed release record while the previous release keeps serving; partial seals are cleaned up. Rollback re-points at existing artifacts (no rebuild, unpublished edits untouched) and refuses already-live, failed, or artifact-missing targets. Each attempt seals into a private staging directory and moves into the final directory atomically under the publish lock; a failing attempt cleans only its own staging tree and uncertain outcomes never delete possibly-activated artifacts. Published origins are per-site loopback listeners resolving the current release per request, so publish/rollback switch content immediately and stay a different origin from the management API; release records are queryable via `GET .../releases/{releaseId}`. HTTP surface: `POST/GET /api/v1/sites/{siteId}/releases`, `GET .../release` (current release + origin URL), `POST .../releases/{releaseId}/rollback` (owner/editor write, member read); OpenAPI (Release/ReleaseCreate/ReleaseFailure schemas plus new Problem codes), generated types, and the route↔operation coverage check updated in the same change (21 operations aligned). Verified with real Node/SvelteKit builds: publish → frozen release.json → origin serves content → unpublished settings edit → second publish switches → live/superseded history → rollback restores the first artifacts with the edit preserved → 409/404/403 boundaries, plus a requiredArtifacts-missing publish returning 422 with the precise missing list, the previous release staying live, the failed record in history, and failed targets not rollback-able; full backend `go test ./...` green. Evidence under `.fuyao/theme-migration/verification/t3b2/`.
