# Management Platform Roadmap (MVP Iteration Ledger)

English | [简体中文](./ROADMAP_ZH.md)

Agile ledger for the content management platform. Each work package lands a running, verified increment; nothing is listed as done before it is implemented and verified. On 2026-11-11 the "Next" section was restructured around the approved theming and React migration track (T1 to T5); the feature packages that follow keep their original scope.

## Done

1. **Backend MVP (local development)** (`admin/backend`): PostgreSQL + SQL migrations, passkey-only WebAuthn auth (discoverable credentials, UV required), CLI (`migrate`, `serve`, `bootstrap-admin`, `create-site`), cookie sessions with CSRF/Origin enforcement, site list/detail/settings with transactional ETag concurrency. Loopback-only. Contract: `contracts/openapi/management.yaml`.
2. **Hardening pass**: transactional first-enrollment closure (advisory lock; concurrent completions admit exactly one), permit expiry re-checked at verify time, full-ETag If-Match binding (wildcard rejected), stable per-session CSRF token (multi-tab safe), request limits and single-object JSON on verify paths, loud TTL validation, CORS ETag exposure.
3. **Admin frontend MVP** (`admin/frontend`): enrollment, login/logout, site list/detail/settings with dirty-field patches, 412 conflict recovery, and viewer read-only; generated API types with drift check; zh-CN/en-US with Crossfade; day/night themes; same-origin dev proxy topology (port 5174 pinned, loopback only). The non-browser protocol integration (backend serve + dev proxy + cookie/origin flows) is exercised by this package's verification; real platform-authenticator ceremonies and visual acceptance remain with the user.
4. **T1 — Theme contract v1** (`contracts/theme/`): machine-checkable contracts for the theme manifest (`theme.json`), the build-input snapshot metadata (`input.json`), and the release metadata (`release.json`), all JSON Schema draft 2020-12, with public-safe positive and negative fixtures covering version, path-traversal, capability, URL-convention, digest, and unknown-field rejections. Consumable validation landed with the contract: Go package `admin/backend/internal/themecontract` (schema compilation, theme-config cross-validation, manifest/input pairing, capability and URL-convention gap helpers) and the `fuyao-admin validate-theme` CLI. Reserved identifiers: first theme `fuyao-homepage`, first trusted adapter `node22-sveltekit-static`. Contract docs: `contracts/theme/README.md`. Verified by `go test ./internal/themecontract/ ./internal/cli/`, `go vet`, `gofmt`, `go build`, prettier, and the repository privacy audit.
5. **T2 — First theme registration** (`site/` as `fuyao-homepage`): `site/theme.json` and `site/theme.config.schema.json` mirror the contract fixtures; `prepare-build-inputs.js` writes `private/input.json` (theme id/version bound to `version.json`, mismatch aborts the build) with the three input digests — public content tree plus the content path/media mapping, site config, theme config — and the `public-config.json` to `site-config.json` rename covers every real consumer (`vite.config.ts`, the build context, `generate-blog-index.js`, `prepare-content-release.js`). `--frozen=<snapshot>` (or `FUYAO_FROZEN_INPUT`) gives T3 a minimal consumption entry: the frozen snapshot is verified read-only (identity, protocol, and digest conflicts are rejected) and only its writable build-asset mirror feeds SvelteKit. Shared logic lives in `site/scripts/lib/theme-input.js`. Verified by `fuyao-admin validate-theme` on `site/`, svelte-check, the 99-test site suite (including four new theme-input tests), lint, a full build, and a normalized artifact diff against a pre-change baseline: 250/250 files, all 99 non-hashed paths identical, remaining differences are `__BUILD_TIME__`/`__sveltekit_` derived asset-hash renames and build-time fields only.
6. **T3-a — Backend theme registry and per-site selection** (`admin/backend`): migration 0003 adds the `themes` catalog and `site_theme_selections`; the operator-driven `fuyao-admin register-theme` CLI (the only registration entry — the HTTP API never accepts paths, commands, or Git addresses) validates a theme root against `contracts/theme`, enforces the trusted-adapter list, resolves the source to the absolute realpath of the validated root, and stores manifest + SHA-256 digest + config schema; re-registration is idempotent only when the full identity (digest and schema, declared/omitted included) matches. HTTP surface: `GET /api/v1/themes` and `GET/PUT /api/v1/sites/{siteId}/theme` under the existing membership/CSRF/Origin/If-Match model with an independent revision counter (`-t` tags, `t0` = unselected); `themeConfig` omission defaults to `{}` while explicit `null` is rejected; invalid configs get a path-free 422; without `FUYAO_ADMIN_THEME_CONTRACTS` the save fails 503 instead of skipping validation. OpenAPI updated with generated types and drift/lint green. Verified against the task PostgreSQL 18 instance: full `go test ./...` plus gofmt/vet/build, catalog-read/persistence/permission/stale-ETag/concurrent-first-save cases, and registration-conflict regressions; evidence under `.fuyao/theme-migration/verification/t3a/`.

7. **T3-b1 — Real snapshot builds and private preview loop** (`admin/backend` + `site/`): migration 0004 persists per-site build tasks whose creation transaction freezes the exact version view (site settings snapshot + revision, theme selection revision, theme identity and config); the executor role is a cluster-wide advisory lock — only its holder recovers interrupted `running` rows as failed and re-enqueues `queued` ones, and it holds the role until its worker drains, so a second instance never kills the first one's active builds. The runner binds every stage to the registered theme root, re-verifies the on-disk `theme.json` and config schema digests against the registered identity (catching post-registration edits), checks the trusted server-side site requirements against the theme's capabilities/URL conventions before building (explicit missing-item failures), runs the theme's own Node preparation with the database-saved settings (`site.name/description/defaultLocale`, description also feeds public SEO metadata via `site.site.description`) and theme configuration injected as JSON files, then seals snapshot and artifacts by **copy + verify + freeze** into per-task directories. Since the workspace-isolation rework, every writing step runs inside the task's private copy of the registered theme root (`taskDir/theme`, excluding node_modules and mutable build state, dependencies resolved from the repository tree, contract schemas injected via `FUYAO_THEME_CONTRACTS`), so the registered source — including its `.fuyao` state and `build/` — is never written, moved, or restored; each task records a full per-file source manifest (aggregate digest plus file count, migration 0005) that is broader than the theme.json digest. Commands run with a scrubbed environment and their own process group (group-kill on cancel), never inheriting database URLs or admin secrets; this is environment and process hygiene, not an OS sandbox. Preview: each succeeded build gets its own loopback-only origin (per-build listener) behind a one-time entry token exchanged for an HttpOnly cookie — root-absolute assets, deep routes, and the declared SPA fallback all behave as in production, builds/sites never cross-serve, and the origin is distinct from the management API so theme scripts cannot read management responses. HTTP surface: `POST/GET /api/v1/sites/{siteId}/builds`, `GET .../builds/{buildId}`, `POST .../builds/{buildId}/preview-links` under the existing membership/CSRF/Origin model; OpenAPI and generated types updated in the same change. Verified against the task PostgreSQL instance: the closed-loop test drives two real API-created builds with real Node/SvelteKit builds through the preview HTTP surface (DB settings frozen into the snapshot, digests recorded, artifacts read-only, second build's origin serving its own content, cross-origin tokens and anonymous access rejected) plus a capability-gap build persisted as an explicit failure; full backend suite, affected site config/theme-input tests, OpenAPI drift check, and prettier green. Evidence under `.fuyao/theme-migration/verification/t3b1/`.

8. **T3-b2 — Publish and rollback closed loop** (`admin/backend`): migration 0006 adds `site_releases` (frozen theme identity, the three input digests, routes, reasons, live/superseded/failed status, persisted failure records) and the `sites.current_release_id` pointer; migration 0007 narrows uniqueness to active releases only (live/superseded) — failed attempts stay in history, the same build can be retried, and republishing a released build answers 409. The `internal/publish` manager re-checks the trusted site requirements (missing capabilities/URL conventions recorded precisely), verifies the manifest's `requiredArtifacts`, generates and contract-validates `release.json` against `release.schema.json`, seals the artifacts by copy + verify + freeze into `ReleasesRoot/<site>/<buildID>`, and switches the live release atomically inside one transaction holding the per-site publish advisory lock (base state read under the lock). Any stage failure persists a failed release record while the previous release keeps serving; partial seals are cleaned up. Rollback re-points at existing artifacts (no rebuild, unpublished edits untouched) and refuses already-live, failed, or artifact-missing targets. Each attempt seals into a private staging directory and moves into the final directory atomically under the publish lock; a failing attempt cleans only its own staging tree and uncertain outcomes never delete possibly-activated artifacts. Published origins are per-site loopback listeners resolving the current release per request, so publish/rollback switch content immediately and stay a different origin from the management API; release records are queryable via `GET .../releases/{releaseId}`. HTTP surface: `POST/GET /api/v1/sites/{siteId}/releases`, `GET .../release` (current release + origin URL), `POST .../releases/{releaseId}/rollback` (owner/editor write, member read); OpenAPI (Release/ReleaseCreate/ReleaseFailure schemas plus new Problem codes), generated types, and the route↔operation coverage check updated in the same change (21 operations aligned). Verified with real Node/SvelteKit builds: publish → frozen release.json → origin serves content → unpublished settings edit → second publish switches → live/superseded history → rollback restores the first artifacts with the edit preserved → 409/404/403 boundaries, plus a requiredArtifacts-missing publish returning 422 with the precise missing list, the previous release staying live, the failed record in history, and failed targets not rollback-able; full backend `go test ./...` green. Evidence under `.fuyao/theme-migration/verification/t3b2/`.

9. **T4 — Admin frontend migration to React + TypeScript + Vite + official Ant Design** (`admin/frontend`): React 18 + react-router 7 + antd 5 (ConfigProvider with zh_CN/en_US locales and the dark algorithm) + Simple Icons (GitHub brand mark); no Svelte runtime remains in `admin/frontend`. Preserved: passkey enrollment/login/logout and session handling, the pinned 5174 same-origin proxy topology (WebAuthn origin unchanged), site list/detail/settings with dirty-field-only patches, If-Match/412 conflict recovery, viewer read-only forms, race-guarded loads, and per-site keyed state (the business modules ported to framework-agnostic stores bound via `useSyncExternalStore`); extended zh/en dictionaries, day/night antd algorithm, and `prefers-reduced-motion` collapsing every animation including antd's. New surfaces: theme selection (catalog + JSON config + If-Match + 412 sync), builds (create, queued/running polling, failure records, private preview links), and releases (current release + published origin, history, publish, confirmed rollback). `pages/` mirrors the routes, `lib/` business modules are JSX-free, and generated `schema.d.ts` types flow through the same OpenAPI chain (api:check green). `npm run admin:check && npm run admin:test && npm run admin:build` all pass (25 tests: client 6, i18n 3, settings editor 8, theme selection 5, mounted views 3). Evidence under `.fuyao/theme-migration/verification/t4/`.

10. **T5 — Joint debugging and local preview delivery**: a dedicated development database on the task PostgreSQL instance (separate from the integration-test database), migrations applied, the management service and the React console dev server started, and the first theme registered; the user receives the URLs, first-run initialization steps (bootstrap-admin permit → enroll the passkey in the UI → create-site → select theme → build → preview → publish → rollback), and exact stop instructions. Real platform-authenticator ceremonies and visual acceptance remain with the user by design.

11. **N1 — App shell, CLI first-run binding, one-time-code login, in-browser site creation** (`admin/backend` + `admin/frontend`): migration 0008 adds `auth_codes` (SHA-256-stored, purpose-bound `init`/`login`, 80-bit codes, attempt burn, 24h purge) and migration 0009 adds site `visibility` (default private) plus `provision_state`/`provision_failure`. `fuyao-admin init-admin`, `login-code`, and `revoke-sessions` join the CLI. `POST /api/v1/auth/exchange` redeems codes transactionally — consumption, purpose enforcement, first-admin activation under the enrollment advisory lock, and session creation commit together, so concurrent redemptions never both win; an in-memory per-address limiter paces the endpoint; every login mints a fresh session. `GET /api/v1/session` reports `platformInitialized` so an uninitialized browser sees exact CLI guidance instead of a login form. `POST /api/v1/sites` creates sites from the UI (slug/theme/visibility validation, optional initial theme selection validated like a theme PUT) and provisions the per-site content/config tree under `FUYAO_ADMIN_SITES_ROOT` with explicit state — DB success alone never marks a site ready — plus idempotent `POST .../provision` retry. The React console gains the desktop shell (grouped sidebar with platform/site scopes and current-site context, sticky top bar with page title and account actions, antd radius tokens 4/8/12), the login-code screen with initialization guidance, the in-browser site-creation wizard with provisioning-state column and retry, and drops the passkey UI (`@simplewebauthn/browser` removed; backend passkey endpoints and data stay, documented as domain-RP-ID-only compatibility — on IP-literal deployments they answer `503 passkey_unavailable` while the server still boots). New env: `FUYAO_ADMIN_TRUSTED_HOSTS`, `FUYAO_ADMIN_AUTH_CODE_TTL`, `FUYAO_ADMIN_SITES_ROOT`, `FUYAO_ADMIN_UI_DIR` (static console hosting with CSP and SPA fallback). OpenAPI, generated types, and the route coverage table updated in the same change (25 operations). Verified: full backend suite green (new tests: init flow with platform probe and reuse rejection, login flow with concurrent single-winner redemption, purpose separation, expiry/stable problem codes, site creation with on-disk provisioning, duplicate slug 409, membership isolation, idempotent provision retry), frontend check/test/build green (35 tests), and a real-binary smoke run from an empty database — migrate → init-admin → uninitialized probe → exchange → create site (`provisionState=ready`, directories on disk, served UI 200) → logout 401 → replay 409 → fresh login-code → re-login sees the site → revoke-sessions. Evidence under `.fuyao/cms-n/verification/n1/`.

12. **N2 — Managed Caddy wiring, preview close + remote entry, first private deployment on the target server** (`admin/backend` + `admin/frontend` + `deploy/fuyao-admin/`): migration 0010 adds `site_network_entries` — one operator-approved port range, unique across kinds, one edge entry per site and one preview entry per build, allocated with a pre-insert trial bind and race retry. Preview origins bind a configured address with platform-allocated ports; issued URLs carry the external base (never the bind address); `POST .../builds/{buildId}/preview-close` revokes tokens, stops the listener, and releases the port idempotently. The `internal/edge` manager renders the managed Caddy snippet from database state (private entries bind exactly the private address, public entries all interfaces), switches per-site `current` pointers atomically on publish/rollback, reconciles drift at startup and on visibility changes, and applies through a fixed operator command (`sudo -n /usr/local/sbin/fuyao-caddy-apply`) with last-good-restore when validate/reload fails; `PUT .../visibility` re-binds a site and `GET .../release` prefers the edge entry URL. Deployment fixes that only real deployment could surface: plain-HTTP trusted hosts no longer mark cookies `Secure` (browsers would silently drop the session), `NODE_OPTIONS` passes through the scrubbed build environment (2 GB host heap tuning), and release site roots are traversable by the reverse-proxy user. Deployed on 149.129.75.59 (Tailscale 100.117.154.115): PostgreSQL 18 local, low-privilege `fuyao-admin` systemd service (cgroup memory limit, 2G disk swap added), built console served by the Go API, theme source package with `npm ci` dependencies, Caddy snippet directory imported once from the operator Caddyfile. Verified end-to-end from an external client over Tailscale: uninitialized probe → init-admin → code exchange → site creation (provisioned on disk) → real theme build succeeding on the server → preview at `http://100.117.154.115:20000` (token exchange 303, page 200) → close (204, old URL refused, port released, idempotent) → publish (live, `edge applied`) → private site served by Caddy over Tailscale (200); public-IP probes to 8787/20000 reach nothing usable (intercepted by the pre-existing tproxy, verified from an external network, egress not via the VPS). Full backend suite and frontend check/test/build green; new integration tests cover preview allocation/external-base/close/reopen and edge publish/visibility/reconcile/apply-failure-restore. Evidence: `.fuyao/cms-n/verification/n2/`; deployment templates in `deploy/fuyao-admin/` (bilingual README, systemd unit, config sample, apply helper).

13. **N3 — Visual site configuration, blog and friends management** (`admin/backend` + `admin/frontend`): the platform becomes the single content authority — `internal/content` jails every read/write inside the per-site tree, renders and parses the exact formats the theme consumes (post frontmatter with `draft` as the public-output gate, friends/social-links YAML, site.yaml), and backs everything with digest ETags (428/412 semantics, atomic temp+rename writes). HTTP surface: posts CRUD (`%2F`-encoded `category/slug.md` paths, search + pagination), friends and social-links document replacement, and the visual site configuration with the AMap security code as a write-only secret (reads report only whether one is set; omitted saves preserve it — covered by a leak regression test). Production-mode builds now resolve per-site `FUYAO_CONTENT_ROOT`/`FUYAO_CONFIG_ROOT`/`FUYAO_FAVICON_ROOT` (the theme script's `/srv/fuyao` deploy lock relocates into the task workspace; new sites seed their favicon set from the theme's defaults so production validation passes). The React console adds the posts page (list/search/pagination, full frontmatter editor + markdown body, draft switch, digest conflict recovery), the friends editor (online/offline groups, ordering, validation), and the site profile page (profile/repository/SEO/services + write-only security code + social links) — navigation grows three sections. OpenAPI, generated types, and route coverage updated in the same change (37 operations). Verified: full backend suite green including a real production-mode closed loop (API-written published post and friends reach the sealed snapshot's `posts/all.json` and `data/friends.yaml`; the draft never does), frontend check/test/build green (37 tests incl. a mounted posts page). Evidence under `.fuyao/cms-n/verification/n3/`.

## Next (in order, one package at a time)

On 2026-11-11 the remaining track was re-planned as packages N1 to N5. Confirmed product constraints for this round: every login is a server-CLI-issued one-time code (no passwords, HTTP login does not depend on passkeys; existing passkey rows and endpoints stay untouched and documented); the admin API, admin UI, and private previews are reachable only from the server host and Tailscale; published sites are public or private per site; access is plain HTTP by IP (no domain, no HTTPS for the new entries); the UI shell follows the desktop-app layout of the robot-platform reference (grouped sidebar, top status/action bar, workspace) implemented with official Ant Design components and tokens.

11. **N4 — Albums and footprint point management**: album/year management with uploads (quota, type and real-file validation, server-controlled storage paths), EXIF/thumbnail processing reusing `site/scripts/generate-album-index.js` as async tasks with failure records, ordering, titles/alt text, and deletion that cannot break media still referenced by live or rollback-able releases; footprint point management over `data/footprints.yaml` with AMap map picking (explicit GCJ-02 storage), list/search/edit/delete. Acceptance: uploads, processing, ordering, editing, deletion, and point saves flow into the same build/publish chain.
12. **N5 — Theme management completion, full joint debugging, final deployment**: registered-theme list with versions/capabilities/config requirements, per-site theme switch with explicit build and publish (never auto-replacing live), concrete capability-gap reporting, preview close surfaced in the UI; end-to-end scenario (initialize → login → create site → configure → edit content → build → preview → close preview → publish → rollback) verified against the deployed server, with the deployed version pinned to a local commit. Acceptance: the end-to-end scenario passes on the server; docs, structure files, and AGENTS rules updated bilingually.

Deferred after this round: membership management UI beyond the current roles, remote theme marketplace/installation, domain binding and HTTPS for platform entries, migration of the remaining `site/scripts` surface (public-data cache, watchers, versioning) not required by N1-N5.

Not planned for MVP: importing production data, migrating real keys, pulling production deployments.
